## 0. How the current 1:1 system actually works (grounding facts)

This matters because the recommendation in §6 leans hard on reusing these pieces unchanged rather than inventing new crypto.

- **Identity/pairing.** `App.tsx`'s `generateContactId()` creates a random client-side ID; the QR code (`myCode`, rendered via `<QRCode value={myCode} .../>` around line 2689) *is* that `contactId`. Whoever scans becomes `role: 'responder'`, the scanned-from side is `role: 'initiator'`. Each contact object (`{id, name, role, ...}`) represents exactly one pairwise relationship — there is no group concept anywhere in the data model today.
- **Connection object.** `WebRTCManager` (`WebRTCManager.js`) wraps exactly **one** `RTCPeerConnection` and **one** `DataChannel`. `RTCStore.js` keeps a single `Map` `chatId → WebRTCManager` (`this.connections`), plus one `sharedSecrets` map and one message-buffer map, all keyed by `chatId`, and `chatId === contactId` everywhere in the app. This 1:1 assumption is structural, not incidental — a group is not just "more contacts," it changes what a "connection" and a "shared secret" even mean.
- **Key exchange.** On `DataChannel.onopen`, the initiator generates a fresh Kyber-768 keypair (`generateKyberKeypair()` → native `KyberModule`, see `HybridCrypto.js`) and sends `{type:'system', subtype:'kyber_pubkey'}` in the clear (pre-secret). The responder calls `kyberEncapsulate()`, gets a `sharedSecret` + `cipherText`, and replies with `{subtype:'kyber_ciphertext'}`. The initiator calls `kyberDecapsulate()`. This happens **fresh on every connection/reconnect** (`WebRTCManager.js` lines ~213-257) — that's where forward secrecy comes from: no persisted long-term secret, a new KEM exchange every session.
- **Message encryption.** `MessageCrypto.js` derives three sub-keys from the one shared secret (`sha256(raw)`, `sha256(raw+1)`, `sha256(raw+2)`) and layers AES-256-GCM → ChaCha20-Poly1305 → XSalsa20-Poly1305. This is **inherently pairwise**: `deriveKeys()` takes exactly one shared secret and produces exactly one triple of sub-keys. There is no key index, no sender-key concept, no per-message ratchet step — reusing it for a group literally means calling `encryptMsg()` once per recipient's own secret.
- **Native crypto surface.** `HybridCrypto.js` only exposes `generateKyberKeypair / kyberEncapsulate / kyberDecapsulate` from the native `KyberModule`. There is **no signature primitive exposed** (no Dilithium/Ed25519, nothing for authenticating "this control message really came from member X" beyond "it decrypted under our pairwise AEAD key"). Any design that wants cryptographic non-repudiation or admin enforcement stronger than "arrived over an authenticated pairwise channel" needs new native code — flagged explicitly as out of scope for v1 in §6.
- **Relay (`relay.js`).** A pure in-RAM, no-disk, no-logs store. Every endpoint is keyed by a **single pairwise identifier** — `token` (initial `/signal/offer|answer`), `contactId` (`/reconnect/offer|answer`, `/call/signal`), or `recipient` (`/packet`, `/receive`, generic fallback). There is no `/group/*` namespace, no roster concept, nothing resembling a "room." The relay never sees plaintext (`payload` is always app-encrypted before it's POSTed) and self-deletes everything (10 min for `/packet` and message-send, 33 days for `/reconnect`, 2 min for `/call/signal`). TURN credentials are short-lived HMAC-signed (`TURN_SECRET`, 6h TTL) — coturn is the same box as the signaling relay.
- **Offline fallback.** `queueOffline()` (App.tsx) persists an encrypted blob to `queue_<contactId>` on disk, tagged with the secret active at enqueue time (`secretUsed`). `flushQueue()` (now in `BackgroundSync.js`, moved out of `App.tsx` for headless/background execution) decrypts with that stored secret and resends once reconnected. Both are **per-contactId**, i.e., already naturally "per relationship" — this generalizes to groups without modification (see §3).
- **System control packets.** `delete_chat`, `clear_chat`, `secret_start/secret_end`, `delete_message`, `device_wiped`, `transfer_ready` all follow the same pattern: sent live over the encrypted DataChannel *and*, if the peer is offline, POSTed to `relay.js`'s `/packet` endpoint (e.g. `App.tsx` line ~669: `POST /packet {payload: JSON.stringify({type:'system', subtype:'delete_chat'}), recipient: chatId}`), picked up by `BackgroundSync.js`'s `runIncomingCycle()`. Replay/order protection is two-layered: `isFreshTimestamp(ts)` (age must be within [-5min, +15min]) and `isNewerThanLastAcceptedSystemTs(contactId, ts)`, a monotonic high-water-mark stored per `contactId` in `AsyncStorage` (`system_ts_hwm_<contactId>`). **Important nuance for §4:** `delete_chat` today is *unilaterally* triggered — either side can delete the shared chat and it propagates to and deletes on the other side automatically. There is no consent/vote step in 1:1. That is exactly the behavior the user wants to avoid making available to a single member against an entire group.
- **Profile updates.** `RTCStore.js`'s `rtc._onKeyExchange` (fires after every fresh Kyber handshake) sends `{subtype:'profile_name'}` and, if changed (hash-compared, `avatar_hash_<chatId>`), a chunked avatar via `sendEncryptedImage()` (`ImageCrypto.js`, 64KB chunks, `img_chunk`/`img_end`, each chunk individually triple-encrypted) followed by a bundled `{subtype:'handshake', hasAvatar, ready:true}`. Removal has its own `profile_avatar_removed` subtype. **Key semantic point:** in 1:1, `profile_name`/`profile_avatar` describe *my own* identity, broadcast independently by each side — there is no "shared canonical value" both sides must agree on. A group name/avatar is different: it's one value all members must converge on. See §5.
- **Cover traffic.** `WebRTCManager.js`'s `_startCoverTraffic()` sends an encrypted dummy packet (64–256 bytes random padding) every 5–15s **per open DataChannel**, for traffic-analysis resistance. This runs per pairwise connection — relevant to the bandwidth math in §2.

## 1. Core cryptographic problem

Two real options, evaluated against *this* app's actual constraints (self-hosted relay, small friend-group scale — not enterprise, existing Kyber/ML-KEM native module, no signature primitive, limited engineering bandwidth for new native crypto):

### Option A — Pairwise fanout (reuse existing 1:1 secrets, no group key at all)

A "group" is a client-side, relay-invisible overlay over the mesh of pairwise 1:1 encrypted channels that already exist between every pair of members. There is no shared group secret. To send a group message, the sender calls the existing `encryptMsg()`/`WebRTCManager.sendMessage()` path once per member, using that member's own already-established pairwise `sharedSecret` (exactly the same object today stored in `RTCStore.sharedSecrets`, just keyed per-member instead of assumed-singular).

- **Crypto reuse:** 100%. Zero changes to `MessageCrypto.js`, `HybridCrypto.js`, or the Kyber handshake in `WebRTCManager.js`. Each pairwise link keeps its own independent Kyber-established secret, re-negotiated fresh on every reconnect exactly as today.
- **Forward secrecy:** *identical* to 1:1, because it literally *is* 1:1 crypto, N-1 times. This also produces a nice emergent property for membership removal (see §6): since no message is ever encrypted under a value shared by the whole group, removing a member requires **no key rotation at all** — you just stop fanning new messages to them. They cryptographically cannot decrypt anything sent after removal, without the app needing to implement any ratchet/rotation logic.
- **Cost:** O(N) pairwise-encrypt-and-send operations per message sent by one member; O(N²) total pairwise connections across the whole group (§2 has the numbers). This is the quoted tradeoff in the task brief, and it is real, but at friend-group scale (≤8-10 members) it's affordable, especially since `FORCE_RELAY_ONLY` and cover traffic already impose comparable per-connection overhead today for every 1:1 chat a user has open.
- **Bootstrapping requirement:** every pair of group members must already be, or become, mutual 1:1 contacts (i.e., have done the QR/deep-link pairing + Kyber handshake with each other directly) — a group is not addressable through a single "hub" member. This is a real UX constraint (see §7 Phase 1) but is *also* what keeps the relay zero-knowledge (§2).

### Option B — Real group key agreement (sender-keys à la Signal, or tree-based like MLS)

A shared symmetric group key (or per-sender "sender key") distributed once via pairwise Kyber exchanges, then used directly for O(1) message encryption regardless of group size, with periodic/ratcheted rotation for forward secrecy and post-compromise security on membership changes.

- **Crypto reuse:** partial at best. The pairwise Kyber KEM (`kyberEncapsulate`/`kyberDecapsulate`) could still be the *transport* for distributing an initial sender key or an MLS `Welcome` message, but the group key schedule, tree ratchet (MLS `TreeKEM`), or sender-key rotation-on-membership-change logic (Signal's model) **does not exist anywhere in this codebase** and there is no signature primitive (§0) to authenticate group-control messages the way MLS requires. Building this well is a significant, easy-to-get-subtly-wrong cryptographic engineering project — implementing your own group ratchet is exactly the kind of thing security reviews in this repo's own commit history (`c266d79`, `5cb3c08`, `f68b491` — "State-Machine-Sicherheitsanalyse", "Adversarielles Claims-Audit") have been hunting bugs in for the *existing*, much simpler pairwise design.
- **Cost:** O(1) message encryption regardless of N — the actual efficiency win the task brief describes — but that win only matters once N is large enough that O(N) pairwise sends become the bottleneck, which (see §2) is well beyond this app's realistic group sizes.
- **Verdict for this app:** not justified. MLS/sender-keys solve a scaling problem (dozens to thousands of members) this app does not have, at the cost of a new crypto subsystem this app has no primitives for and no track record of building safely yet. Pulling in an external MLS library (e.g. OpenMLS) would also be a large, unreviewed native-dependency addition to a project that has clearly invested heavily in auditing its *current* small crypto surface.

### Recommendation

**Option A (pairwise fanout, no group key)** for v1 — see §6 for the full commitment and explicit punts. Reconsider Option B only if a later requirement genuinely needs groups larger than ~15-20 members or admin-enforced membership with cryptographic non-repudiation, at which point it's a good candidate for a from-scratch design effort (with a signature primitive added to `HybridCrypto.js`/`KyberModule` first).

## 2. Relay/rendezvous implications

Today `relay.js` brokers exactly one pairwise relationship per identifier (`token`/`contactId`/`recipient`). With Option A, **no new relay endpoints are strictly required for connection establishment** — every pairwise link inside a group is, from the relay's point of view, indistinguishable from an ordinary 1:1 pairing: it reuses `/signal/offer|answer` (or `/reconnect/offer|answer` for reconnects) keyed by that pair's own `contactId`, exactly as today. The relay does not need to know a "group" exists at all for the WebRTC signaling layer.

New relay-visible surface is only needed for **group-level metadata that doesn't map onto a single pairwise relationship**: group deletion votes and group profile updates. Even those can piggyback on the existing generic `/packet` endpoint (`POST /packet {payload, recipient}`) — sent once per member, with `recipient` = that member's own `contactId` and the group identity embedded *inside* the encrypted `payload` (a `groupId` field, meaningless to the relay). **No new relay code is required at all** for the MVP — only new *client-side* looping over the existing per-member endpoints.

### Is zero-knowledge still achievable?

Content: yes, unchanged — the relay still only ever sees opaque `payload` blobs and never learns groupId, membership, or content, because Option A never asks the relay to route anything by group identity.

Metadata: **partially, with an explicit, honest caveat.** The relay already learns pairwise contactId adjacency for 1:1 chats (who is polling whose `/packet`, who is exchanging `/signal` tokens, who is registered for push under which `contactId`). Grouping doesn't add a new *category* of leak, but it does let a relay operator who is also logging traffic timing (self-hosted, so this is "you, if compromised" not "an unrelated Malachi operator") correlate that several contactId pairs are being used in a temporally-clustered way (e.g., five pairwise `/packet` POSTs firing together every time one member sends a group message) and infer a group probably exists among those five contactIds, without ever learning a "groupId" as an explicit token. This is unavoidable in *any* server-mediated design that doesn't hide traffic timing (onion-routing-style mixing, which is out of scope) — including Option B, which would still need *some* rendezvous mechanism unless membership discovery happened purely out-of-band. Recommendation: **document this explicitly to the user** as "the relay cannot read your group's messages, membership list, or content, but a compromised or logging-enabled relay operator could statistically infer that several of your contacts talk to each other in a correlated pattern" — this is honest and consistent with the project's existing "zero-knowledge relay" framing (it already accepts a comparable caveat for 1:1: the relay sees *that* two contactIds are exchanging packets, just not what's in them).

To *minimize* this further without a redesign: add jittered send timing for group fanout (stagger the N-1 pairwise sends by a random 0-2s delay instead of firing them synchronously) — cheap, and directly analogous to the existing cover-traffic jitter pattern (`Math.floor(Math.random() * 10000) + 5000` in `_startCoverTraffic`).

### Full-mesh bandwidth/connection-count math

With Option A, a group of size N requires every member to hold a live pairwise connection to every other member (full mesh) for live P2P delivery — mirroring exactly how 1:1 works today, just N-1 times per member.

| N (members) | Total pairwise connections (mesh) | Connections per member | Pairwise sends per group message (sender's cost) | Concurrent cover-traffic streams (whole group) |
|---|---|---|---|---|
| 5  | 10  | 4  | 4  | 10  |
| 10 | 45  | 9  | 9  | 45  |
| 20 | 190 | 19 | 19 | 190 |

- **Connection count grows O(N²)** across the group as a whole (standard handshake math, `N(N-1)/2`) — this is a real, structural cost of full mesh, not a message-cost artifact.
- **Per-message bandwidth for the sender grows O(N)** (linear): sending one group text means N-1 individual `encryptMsg()` + `dataChannel.send()` calls, each traversing the relay's TURN allocation once (`FORCE_RELAY_ONLY`), so **each pairwise send roughly doubles through the relay** (client→relay, relay→client) — total relay-transited bytes per group message ≈ `2 × (N-1) × messageSize`.
- **Aggregate group bandwidth over time is effectively O(N²)** once you account for every member being a potential sender proportionally as often as any other — this is the standard full-mesh chat cost profile and is the real reason to cap group size (§6), not the per-message linear cost alone.
- **Idle/standing cost matters more than message cost here** because of cover traffic: every one of the `N(N-1)/2` pairwise DataChannels independently runs `_startCoverTraffic()` (5-15s interval dummy packets) *permanently while open*, regardless of whether anyone is actively chatting. At N=20 that's 190 always-on low-rate streams through one home coturn box — each is small (64-256B every ~10s ≈ single-digit bytes/sec) but 190× that, plus 190 TURN relay allocations held open concurrently (each with its own STUN/TURN refresh traffic), is a materially different load profile for a residential upload link than the "a handful of 1:1 chats" case this relay was built and tuned for (`coturn-ipv6-update.*` scripts, DuckDNS dynamic DNS, the whole `relay_infra_health_check` playbook in the user's own memory file is scoped to a single home box).

This table is the concrete basis for capping group size in §6 — not an arbitrary product decision, but a direct consequence of `FORCE_RELAY_ONLY` plus the existing per-connection cover-traffic design running on self-hosted infrastructure.

## 3. Message delivery model generalization

**Does every member need a live connection to every other member?** Under Option A, yes for live P2P delivery — there is no relay-side fanout/multicast (`relay.js` has no concept of "deliver to N recipients," only single-`recipient` addressing), and there's no shared group key that would let one relayed blob be meaningfully decrypted by multiple recipients anyway. So live delivery is inherently mesh-shaped.

**What happens when some members are offline?** This generalizes *for free* from the existing per-contact design, because `queueOffline()`/`flushQueue()` and the relay's `/packet` fallback are already keyed per-`contactId`, not globally:

- Sending a group message = loop over `groupMembers`, and for each member: if `RTCStore.isConnected(memberId)` is true, use the live path (`WebRTCManager.sendMessage`, same as 1:1 `sendMessage(chatId, text)` in `RTCStore.js`); if not, enqueue via the existing `queueOffline()` pattern under `queue_<memberId>` exactly as a 1:1 offline message would, and/or POST to `/packet` with `recipient: memberId` for the relay-fallback path (same code shape as the `delete_chat` fallback at `App.tsx` line ~669).
- **Does sender-fanout multiply offline relay-queue storage cost by group size?** Yes, linearly and by design — a group message to a group where M of N members are currently offline creates M separate `/packet` entries on the relay (one per offline member's `contactId`), each independently expiring after the existing 10-minute TTL. This is not a new storage *model*, just M times the existing per-contact cost. Given the relay is RAM-only with aggressive auto-expire (`EXPIRE_MS = 10 * 60 * 1000`) and already caps `transfer_` entries at 100 with LRU eviction (`relay.js` cleanup interval), this scales acceptably at friend-group sizes (a burst of ~20 packets from one group message to an all-offline 20-member group is trivial RAM for a Node process) but is worth monitoring if group *count* per user grows — recommend no relay-side change for v1, just note it as a scaling axis if usage patterns change.
- **Local queue storage** similarly multiplies: today one offline message to one contact writes one `.enc` file + one queue index entry. A group message to M offline members writes M such entries (same file format, different `queue_<memberId>` indices) — this is `O(M)` local disk, not `O(1)`, and should be sized against `RNFS` limits on the device but is not expected to be a real constraint for text/typical image/audio volumes at this group scale.
- **Chunked transfers (images/audio, `ImageCrypto.js`/`AudioCrypto.js`, 64KB chunks)** generalize the same way — sending a group photo means running `sendEncryptedImage()` (or its offline sibling `sendEncryptedImageOffline()`) once per member, each independently chunked and encrypted under that member's own pairwise secret. This is the most bandwidth-sensitive case: a group photo to a 10-member group is 9 independent full chunked transfers, not 1 — worth flagging to the user in UI ("sending to 9 people...") rather than silently, and a good candidate for the size-cap discussion in §6.

## 4. Wipe-all / vote-based deletion

### Extending the existing pattern

The existing `delete_chat` system packet (`{type:'system', subtype:'delete_chat', ts, ...}`, replay-protected via `isFreshTimestamp` + `isNewerThanLastAcceptedSystemTs`) is **unilateral**: either 1:1 party can trigger it and it deletes on both sides automatically, no consent step. Mapping that directly onto a group ("wipe all" = any single member nukes history for everyone) is exactly the blast-radius problem the user flagged, which is why they explicitly asked for the vote alternative.

Recommend implementing **both**, gated by who's allowed to trigger which:

**A) Admin/creator "wipe all"** — mirrors 1:1 `delete_chat` exactly, but restricted to the group creator (or a small admin set), stored client-side in the local group metadata object (`{groupId, createdBy, admins: [...]}`) — not cryptographically enforced (no signature primitive, §0/§6), just a UI/logic-level restriction. New system packet `{type:'system', subtype:'group_wipe', groupId, ts}`, fanned out to every member via the same per-member loop described in §3 (live P2P where connected, `/packet` fallback otherwise). Each recipient checks locally that the sender is a known admin of `groupId` before honoring it — this is a **soft** check (a compromised/malicious peer who already has your pairwise shared secret and knows the groupId could forge this, same trust boundary as literally every other system packet in this app today, e.g. nothing cryptographically stops your existing 1:1 peer from sending a bogus `delete_chat` either — that's accepted as within-model since the pairwise AEAD already authenticates "this came from the peer I Kyber-handshook with," not "this peer is authorized to do X").

**B) Vote-based deletion** (the harder, more interesting one, and the one that actually needs new design):

- **Who can initiate:** any member (this is the point — it's the mechanism that doesn't require a single admin).
- **New system packet types**, fanned out per-member exactly like §3's message fanout:
  - `group_delete_vote_start {groupId, ballotId, initiator, ts}` — `ballotId` = a fresh random nonce chosen by the initiator, **not derived from `ts`**. This is important: unlike `delete_chat` (a one-shot terminal action per relationship, so a monotonic timestamp alone is sufficient replay protection), a group deletion vote can fail to reach quorum and be legitimately re-initiated later. Keying replay protection purely off a monotonic per-`groupId` timestamp (the direct analog of `isNewerThanLastAcceptedSystemTs`) is not enough by itself, because it doesn't distinguish "this is a new vote round" from "this is the same vote round, delivered again" — you need the high-water-mark check keyed on `(groupId, ballotId)` pairs (accept the first packet for each new `ballotId` that is also fresh/in-order; reject a replayed packet reusing an already-resolved `ballotId`).
  - `group_delete_ballot {groupId, ballotId, voter, choice: 'yes', ts}` — cast by each member, fanned to every *other* member (not just back to the initiator — no central tallying authority is trusted, so every member independently tallies from the votes it directly received, consistent with the "relay must not be trusted to tally" requirement).
  - `group_delete_executed {groupId, ballotId, ts}` — optional, sent by whichever member's local tally first reaches quorum, so others converge faster instead of waiting for their own count of straggling votes; still just a hint, each member should also finalize on its own tally once its local timeout expires, not solely trust this packet (a malicious peer could send a false "executed" early — treat it as "check your own tally, and if it also indicates quorum, execute; otherwise treat as a signal to poll relay `/packet` more eagerly, not as authoritative").
- **Authentication of votes:** a `group_delete_ballot` arriving over a specific pairwise DataChannel (or, offline, decrypted successfully under that specific member's pairwise secret via the `/packet` fallback) is authenticated as "genuinely from that member" by the same AEAD-over-pairwise-secret property every other system packet relies on today (§0) — the relay cannot forge a vote it can't decrypt, and cannot inject a vote without the sender's pairwise key. What the relay (or a malicious member) *can* do is **selectively withhold or delay delivery** of specific members' votes to specific other members — this is a real, honestly-documented limitation (see below).
- **Threshold:** recommend **majority of the group's current member list** (`memberContactIds.length`), not majority of votes cast, to avoid a fast-moving minority forcing deletion while others haven't seen the vote yet. Add a **timeout** (recommend 7 days, configurable) after which an unresolved vote auto-expires (a fresh `group_delete_vote_start` with a new `ballotId` can be initiated again later) — without a timeout, a vote that never reaches quorum (e.g., one member permanently offline) leaves the group in limbo forever from the perspective of members still trying to tally it.
- **Replay/forgery specifics:** reuse `isFreshTimestamp` unchanged (15-min window is fine for the packet's own freshness), but the ordering check must be `(groupId, ballotId)`-scoped, not the flat per-`contactId` `isNewerThanLastAcceptedSystemTs` — recommend a new function e.g. `isValidGroupBallot(groupId, ballotId, voter, ts)` that (a) rejects if `ballotId` doesn't match the currently-open vote round for that group (prevents replaying a ballot from a past, already-resolved round), and (b) rejects a second vote from the same `voter` in the same `ballotId` (prevents a captured single ballot from being replayed to inflate the tally — dedup on `(groupId, ballotId, voter)`).
- **Honest limitation to document for the user:** because there is no trusted tallying authority and no signature scheme, **a member who is offline for the entire voting window simply doesn't get a vote counted**, and a relay operator who selectively drops specific members' `/packet` fallback deliveries could in principle suppress specific votes from being seen by specific members (skewing what each member's *local* tally looks like, potentially making the vote resolve differently for different members if they never reconcile). This is a real, non-hypothetical gap in a zero-trust-relay design without a broadcast/gossip layer — flag it plainly rather than claiming the vote is tamper-proof. Mitigation for v1: none beyond timeout-based re-initiation; a real fix (per-member gossip/reconciliation of received ballots, or moving to a signed-ballot + majority-of-signed-broadcasts scheme) is a good Phase 7+ candidate, not v1.
- **Applying "wipe" consistently without a central authority:** once a member's local tally (or a trusted-enough `group_delete_executed` hint, re-verified locally) reaches quorum, that member deletes local group state exactly like `wipeContactLocally()`/`delete_chat`'s handler does today (`EncryptedStorage.removeItem('chat_' + groupId)`, remove from local groups list, clear `queue_<memberId>` entries for now-irrelevant fanout, etc.) — this is a straightforward extension of the existing per-contact wipe code path (`wipeContactLocally` in `BackgroundSync.js`), just targeting a `groups` storage key instead of `contacts`.

## 5. Group profile picture/description

The wire mechanics reuse existing code directly:
- Chunked avatar transfer: `sendEncryptedImage()`/`ImageCrypto.js` unchanged, reused as-is (64KB chunks, `img_chunk`/`img_end`), just tagged so the receiver routes it to "group avatar" storage instead of "contact avatar" storage (mirroring the existing `isAvatarChunk` flag threading already present in `RTCStore.js`/`WebRTCManager.js` for 1:1 profile avatars — extend with e.g. `isGroupAvatarChunk` + `groupId`, or better, a single `avatarScope: {type:'group', groupId}` field, since a device may need to handle group-avatar chunks concurrently with 1:1-avatar chunks from different pairwise connections).
- Name/description update: a new system packet `{type:'system', subtype:'group_profile_update', groupId, name, description, hasAvatar, ts, updatedBy}`, fanned out via the same per-member loop as §3/§4 (live P2P + `/packet` fallback).

**Semantic difference from 1:1 profile that matters:** 1:1 `profile_name`/`profile_avatar` are *independent, per-side* — Alice's name-as-seen-by-Bob and Bob's name-as-seen-by-Alice are two unrelated values, each side broadcasts their own. A group name/avatar/description is a **single canonical value all members must converge on** — this is a genuinely different data-consistency problem (eventual-consistency-with-conflict-resolution, not "each side owns their own field"), even though the transport code is identical.

- **Who can change it:** punt to "any member can change it" for v1, exactly mirroring how the current 1:1 profile update is unrestricted (either side can just start sending a new name/avatar whenever they like — no permission model exists there either). This is the simplest option and consistent with how small-group messengers (WhatsApp/Signal groups, by default) commonly behave. Document as an explicit, revisitable tradeoff: a later "admin-only" restriction is a pure client-side/UI gate (same caveat as §4's admin wipe — not cryptographically enforced without a signature primitive) and can be added later without a wire-format change (the `updatedBy` field is already present for a receiver to apply such a check).
- **Propagation:** same per-member fanout as messages/votes — no new relay involvement.
- **Ordering/replay protection:** yes, needs the same protection class as other system control packets, but with **last-write-wins conflict resolution** rather than "reject anything not newer" in the strict `delete_chat` sense, because two members could plausibly both update the group name around the same time (unlike `delete_chat`, which is meant to be a one-shot terminal action). Recommend: per-`groupId` monotonic high-water-mark (`isNewerThanLastAcceptedSystemTs`-style, keyed by `groupId` not `contactId`) so only the packet with the highest `ts` "wins" and is applied — a member who's briefly offline and receives an out-of-order batch on reconnect converges to the same final state as everyone else, since they all apply the same "highest ts wins" rule independently. This reuses the *pattern* from `BackgroundSync.js`'s existing `isNewerThanLastAcceptedSystemTs(contactId, ts)` almost verbatim, just re-keyed.
- **Local storage:** mirror the 1:1 pattern (`avatar_hash_<chatId>` hash-compare to avoid re-sending unchanged avatars) as `avatar_hash_group_<groupId>`, and a `group_<groupId>` metadata blob (name, description, avatarUri, memberContactIds, admins, createdBy, createdAt) in `EncryptedStorage`, parallel to how `contacts` is stored today (and reusing the exact same `updateContacts`-style write-serialization pattern from `BackgroundSync.js` — see §7 Phase 0 — to avoid reintroducing the lost-update race that `updateContacts()`/`withQueueLock()` were specifically built to fix for the contacts list).

## 6. Concrete recommendation

Build **Option A (pairwise-mesh fanout, no shared group key)**, as a client-side/UI-and-routing feature layered entirely on top of the existing 1:1 primitives, with these explicit v1 decisions:

1. **Cap group size at 8 members for v1** (hard client-side limit, easy to raise later once real usage data exists). Rationale is the §2 table: at 8 members you're at 28 mesh connections / 7 cover-traffic streams per member — comparable in order of magnitude to a moderately active user's existing 1:1 contact list, and safely within what a home coturn box was already being tuned for (see the user's own `relay_infra_health_check.md` memory note — this is explicitly a single home server, not cloud infrastructure sized for O(N²) mesh at N=20+).
2. **No shared group key, no group key rotation, no group ratchet.** Every message is pairwise-encrypted N-1 times under each member's own existing (or newly-established) 1:1 Kyber-derived secret. This is a deliberate, documented tradeoff: it means **weaker efficiency** (O(N) sends per message) in exchange for **zero new cryptographic attack surface** and a forward-secrecy story that fully piggybacks on the already-audited 1:1 design. As noted in §1, this also gives membership removal "forward secrecy" for free (no rotation needed — a removed member simply stops receiving new pairwise sends and was never able to decrypt anything under a value shared with people who remain).
3. **Groups require full mutual pairing.** A group can only contain members who are (or become, via the existing QR/deep-link 1:1 pairing flow, unmodified) each other's mutual 1:1 contacts. This is the mechanism that keeps the relay's view unchanged (§2) and reuses 100% of the existing pairing UI/flow — no new pairing protocol.
4. **Both deletion mechanisms**, gated as described in §4: creator/admin "wipe all" (mirrors `delete_chat`, soft-authorized client-side) *and* member-initiated majority vote with a 7-day timeout, `ballotId`-scoped replay protection, and an honestly-documented limitation around offline members / a relay that selectively withholds deliveries.
5. **Group profile (name/avatar/description) editable by any member for v1**, last-write-wins via a per-`groupId` monotonic high-water-mark, admin-only restriction explicitly punted (easy follow-up, no wire-format change needed).
6. **No relay code changes required for v1.** Every new capability (message fanout, votes, profile updates) rides the existing `/signal`, `/reconnect`, `/packet`, and `/transfer` endpoints, addressed per-member exactly as 1:1 traffic is today. `relay.js` stays untouched.
7. **Explicitly punted, and why:**
   - *Real group key agreement / MLS-style ratchet* (Option B) — not justified at this scale; revisit only if group size requirements grow past ~15-20 or admin-enforcement needs to be cryptographic (§1).
   - *Cryptographic admin enforcement / non-repudiation* for wipe-all and profile edits — requires a signature primitive not currently exposed by `HybridCrypto.js`/`KyberModule`; both are left as soft, client-side-checked permissions for v1 (§4, §5).
   - *Defense against a relay that selectively drops/delays specific members' votes or messages* — accepted as an existing-class risk (the relay already can selectively drop any 1:1 packet today; groups don't introduce a new risk *category*, just more surface for it), mitigated only by the vote timeout/re-initiation mechanism, not solved.
   - *Group voice/video calls* — `CallManager.js` is also strictly pairwise today (`contactId` + `direction`-keyed signaling, same pattern as `relay.js`'s `/call/signal`); group calls hit the mesh-of-relayed-media problem even harder (media bandwidth, not just small control packets) and should be a separate, later design effort, not bundled into v1 group chat.
   - *Groups larger than the v1 cap* — explicit fork-in-the-road noted in §1/§2: if this becomes a real requirement, that's the point to design a real group-key scheme, likely alongside adding a signature primitive to the native crypto module.

## 7. Implementation phasing

Each phase is independently testable and, where relevant, should mirror the existing test patterns under `__tests__/security/` (e.g. `stateMachine.pollCycleGuard.test.js`, `stateMachine.initiatorPacketPollGap.test.js`, `concurrency.contactsStorageLostUpdate.stillIncomplete.test.js`) for the new group-scoped state machines and storage races.

**Phase 0 — Data model.**
New `groups` storage key (parallel to `contacts`), one entry per group: `{groupId, name, description, avatarUri, memberContactIds: [], admins: [], createdBy, createdAt}`. Reuse the `updateContacts()`-style serialized-write-chain pattern from `BackgroundSync.js` (a `updateGroups(mutator)` following the exact same `contactsWriteChain` shape) to avoid reintroducing the lost-update race that pattern was built to fix. Groups list UI (new screen, no crypto). *Testable independently*: pure storage/serialization tests, no networking.

**Phase 1 — Membership bootstrapping.**
"Create group from contacts" flow, selecting from already-paired 1:1 contacts only. "Add member" flow: if the new member isn't already a mutual 1:1 contact of *every* current group member, surface that clearly and drive each missing pair through the existing QR/deep-link pairing flow before the member is considered fully joined. *Testable independently*: UI/flow test, can be validated against a small in-memory contacts fixture without live WebRTC.

**Phase 2 — Message fanout.**
New `group_text` message type. Sending: loop `memberContactIds`, per member either live `RTCStore.sendMessage(memberId, ...)` or the offline `queueOffline()` path, tagged with `{groupId, senderContactId}`. Receiving: tag inbound messages with sender attribution for the UI (name/avatar sourced from the existing per-pair `profile_name`/`profile_avatar` already known for that member — no new identity data needed here). *Testable independently*: mock N `WebRTCManager` connections, assert fanout loop calls the right per-member send/queue path based on connection state.

**Phase 3 — Group-scoped local chat storage.**
`chat_<groupId>` key holding merged inbound messages from all members, same shape/patterns as `chat_<contactId>` today (read/delete/clear code paths reused, just re-keyed).

**Phase 4 — Group profile (name/avatar/description).**
`group_profile_update` system packet, fanned out via Phase 2's loop; chunked avatar reuse (`ImageCrypto.js` unchanged); per-`groupId` monotonic high-water-mark for last-write-wins (new function alongside `isNewerThanLastAcceptedSystemTs`, same shape, different key). *Testable independently*: feed out-of-order `group_profile_update` packets into the ordering-check function and assert only the highest-`ts` one is ultimately applied, mirroring the existing replay-order tests' structure.

**Phase 5 — Deletion: admin wipe-all + member vote.**
`group_wipe` (soft-admin-checked, mirrors `delete_chat`) and the `group_delete_vote_start`/`group_delete_ballot`/`group_delete_executed` flow from §4, including the `(groupId, ballotId, voter)`-scoped replay/dedup function and the 7-day timeout re-initiation path. *Testable independently*: this is the highest-value target for state-machine-style tests analogous to the existing `stateMachine.*.test.js` files — simulate ballots arriving out of order, duplicated, from a stale `ballotId`, and past-timeout, and assert the tally/execution logic behaves as specified.

**Phase 6 — Concurrency/security pass.**
Dedicated review pass mirroring the project's existing practice (see commit history: `c266d79`, `5cb3c08`, `e9a29aa`, `f68b491` are all prior "security/state-machine review" commits) specifically against the new group code: lost-update races on the new `groups` storage key (same class of bug `updateContacts()`/`withQueueLock()` fixed for contacts), replay/ordering edge cases in the vote and profile-update high-water-marks, and confirmation that `FORCE_RELAY_ONLY` is still honored on every one of the new mesh connections (no accidental direct-IP path introduced by looping connection setup).

**Phase 7 — Explicitly deferred (not v1).**
Group voice/video calls, cryptographic admin enforcement (needs a signature primitive), gossip/reconciliation defense against selective vote/message withholding by a malicious relay, and any redesign toward a real group-key scheme if group-size requirements grow past the v1 cap.

## Open questions that still need a human decision

- Exact v1 group size cap (this document proposes 8; the §2 table gives the data to pick a different number if desired).
- Whether "any member can leave, but only admin/vote can remove others" is the intended membership-removal model (not fully specified in the user's brief) — removal-by-others needs the same "who's authorized" question as wipe-all/profile-edit, and this document has not designed a "kick a member" flow at all (only join/add and whole-group deletion). Worth scoping explicitly before Phase 1.
- Whether the 7-day vote timeout is the right default, and whether it should be configurable per-group at creation time.
- Whether group avatar/description should eventually get admin-only restriction by default (v1 recommendation is "any member," see §5) — a product decision, not a technical constraint.
